# Recommendations and feedback — FR08–09 / NFR02–03,06,08,11

Phase4 follows accepted learning/marketplace gates. Existing auth/CSRF/error conventions.

GET `/recommendations?limit=10` student-only, limit1–20. Return `{listings:[{item:Listing,score:number,reason:string}],content:[{item:Content,score:number,reason:string}],mode:'profile'|'hybrid'|'general',alpha:number,limitations:string[]}`. Items are actual response projections from current services, never mock records. Published verified-company listings only; no closed/draft/unverified items. Published learning only. Stable deterministic ordering and bounded candidate pool (document cap).

Start with TF-IDF/profile cosine using current student's program, skills, interests and location, and eligible title/description/skills or resource title/body/tags. Cold start has alpha1. Missing profile uses actual interaction popularity if available, otherwise recent eligible publications; reason must name actual fallback, not fictional matching/popularity. Suggestions are not placement or hiring decisions.

Hybrid component uses observed optional explicit ratings only. Minimum implementation thresholds: >=5 distinct users, >=20 explicit user/item ratings and at least2 observed common items per neighbor. Compute similarity on jointly observed items; never impute missing feedback as numericzero labels. Normalize observed1–5 ratings. For an item with valid neighbors, combine normalized content/collaborative scores using alpha. Otherwise alpha1 for that item. Implement validated0–1 configuration `APP_RECOMMENDER_ALPHA` default1 until an actual held-out evaluation chooses a weight. Explain this pending validation limitation. Tests can configure non1 weight on clearly synthetic fixtures; no pilot effectiveness claim. Default production/local behavior remains valid profile ranking rather than an unvalidated numeric claim.

POST `/interactions` student/instructor only, body `{item_type:'listing'|'content',item_id:UUID,event_type:'view'|'rating',rating?:int}`. User/time derived server-side. Extra user_id/timestamp rejected. Referenced item must be eligible/published; enforce typed foreign keys/checks, not orphan UUID records. rating strictly integer1–5 only for event_type rating; view has no numericrating. Store/update one latest explicit rating per user/item idempotently; views are actual events. Bound per-user write frequency. Response `{id,item_type,item_id,event_type,rating,created_at}`. Do not invent ratings from saved/reacted/viewed/applied behavior.

Frontend: suggestions screen with actual reason, profile-edit path, clear fallback/empty/unavailable states; link to actual listing/resource detail. Optional unselected relevance rating1–5 with explicit Submit button and feedback-use explanation; no effect on application decisions. Post view events only for actual detail openings; failing passive telemetry must not break applications. Registration/privacy text explains profile/activity use; pilot retention/consent policy remains unresolved rather than fabricated.

Tests: deterministic profile ranking; recent/actual-popularity cold start; closed/unverified/unpublished exclusion; role/foreign-user assignment denial; unknown item/invalid numericrating rejection; timestamp/user derivation; rating upsert; actual view has nullrating; synthetic eligible-neighbor hybrid and insufficient-data alpha1 fallback. No new measured research claim.
